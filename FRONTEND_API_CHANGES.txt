6. RESPONSE FORMAT CHANGE — ERROR RESPONSES
-----------------------------------------------------------

  Errors now return a unified envelope instead of varying formats.

  OLD (inconsistent):
    { "detail": "some error message" }
    { "field": ["error"] }

  NEW (unified):
    {
      "error": true,
      "detail": "Human-readable message",
      "code": "machine_readable_code",
      "errors": { "field": ["validation error"] }   // present on validation errors only
    }

  The "detail" key is still present — but now always nested under "error: true".
  The "errors" key contains field-level validation errors (replaces bare field errors).


-----------------------------------------------------------
7. BEHAVIOUR CHANGES (no URL change, but affects frontend logic)
-----------------------------------------------------------

  a) Favourite Locations — max 20 limit enforced
     - POST /api/v1/locations/favourites/ will return 403 if user already has 20 saved.
     - Frontend should check count before allowing the user to save more.

  b) OTP — brute-force lockout after 5 wrong attempts
     - POST /api/v1/auth/verify-email/ and /reset-password/ will return 400
       with "Invalid or expired OTP." after 5 failed attempts for the same OTP.
     - Frontend should show an appropriate message and direct user to request a new OTP.

  c) Health check now includes DB status
     - GET /api/v1/auth/health/
     - Returns 503 with { "status": "degraded", "db": "unavailable" } if DB is down.
     - Old behaviour always returned 200.

  d) X-Request-ID header on every response
     - Every response now includes an "X-Request-ID" header (UUID).
     - Useful for correlating frontend errors with backend logs — consider logging it.


-----------------------------------------------------------
8. AUTHENTICATION — NO CHANGE
-----------------------------------------------------------

  Still uses token-based auth (DRF Token).
  Header format unchanged:
    Authorization: Token <token_value>
